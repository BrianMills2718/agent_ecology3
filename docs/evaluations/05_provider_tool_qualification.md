# Evaluation 05: Provider, Prompt, and Tool Qualification

**Preregistered:** 2026-08-11 (before any Evaluation 05 model call)
**Stage:** Exploratory instrument qualification
**Decision owner:** Brian Mills
**Lifecycle effect:** None; AE2 and AE3 remain separately active

## Claim and decision

Falsifiable claim: with the repaired async runtime and the frozen output and
timeout settings below, the selected `minimax/minimax-m3` route can return a
legal AE3 action through the exact `ae3_action` tool contract reliably enough
that provider/tool failures will not dominate a later 16-call behavioral run.

Decision after this assay:

- **Qualified:** each cognition prompt produces at least 15 usable actions in
  16 attempts; neither condition has a timeout or output-truncation failure;
  every attempt has exact trace linkage; and every successful tool action is
  identical to the `response_tool_calls` payload reopened from `llm_client`.
- **Not qualified:** any other terminal result. Do not begin a behavioral
  comparison on this instrument.
- **Invalid assay:** frozen input/hash mismatch, missing evidence manifest,
  local positive/negative control failure, concurrent dispatch, retry, or spend
  above the aggregate cap. Repair the assay itself and preregister a new
  evaluation number rather than reclassifying this one.

This assay can qualify an instrument. It cannot show emergence, downstream
economic value, equivalence of cognition prompts, or a prescription effect.

## Units and frozen cases

One unit is one independent model call against a deterministic visible-state
fixture. There are 32 serial attempts: 16 `prescribed` and 16 `minimal`, ordered
in alternating condition pairs across four principal strata and four rounds.
No model response changes a later call's prompt or state.

For each principal `alpha_1` through `alpha_4`, the call uses:

- the condition's committed prompt file;
- that condition's normal bootstrap strategy text for the principal;
- the state template in `config/evaluations/05_fixed_state.json`, with
  `${principal_id}` replaced by the stratum ID;
- the exact `ae3_action` schema generated by the production loop runtime; and
- the production system instruction: “Choose one AE3 action. Prefer tool call
  ae3_action when available; else return exactly one JSON action object. No
  prose.”

The runner must preserve the rendered messages, tool schema, effective config,
and their SHA-256 hashes before dispatch. Provider sampling remains stochastic;
case order, state, prompts, schema, parser, and thresholds do not.

## Frozen provider and spend contract

| Setting | Frozen value |
|---|---|
| model | `minimax/minimax-m3` |
| retries | `0` |
| timeout | `90` seconds per call |
| maximum output | `4096` tokens |
| calls | `16` per prompt, `32` total |
| dispatch | serial only |
| root budget | USD `0.20` per condition |
| aggregate configured ceiling | USD `0.40` |
| budget reservation | USD `0.01` per dispatch |

The larger output allowance and timeout are fixed from Evaluation 04's observed
1,024-token truncations and one 60-second timeout; they are instrument settings,
not post-result changes. Stop a condition on budget exhaustion. No fallback
model, retry, response repair call, extra case, or replacement attempt is
allowed.

## Outcome classification

Each attempt receives exactly one terminal class:

- `usable_tool_action`: provider success; exactly one matching `ae3_action`
  tool call; arguments decode to one object; the action passes AE3's production
  intent parser; and durable shared-client tool payload is identical.
- `usable_json_action`: provider success; no tool action; response contains one
  action object accepted by the production parser. This counts toward usability
  but does not waive tool-custody checks for calls that did use a tool.
- `provider_timeout`, `output_truncation`, `provider_error`,
  `missing_or_malformed_action`, `illegal_action`, `trace_failure`, or
  `custody_failure`.

The primary measure is usable actions divided by all attempts, separately by
prompt. The frozen 15/16 threshold (93.75%) leaves at most one non-timeout,
non-truncation failure before a later behavioral floor of 12/16 valid actions
would become instrument-sensitive. Results are descriptive at this sample
size; no confidence or equivalence claim is planned.

## Controls

Before paid dispatch:

1. a deterministic well-formed `ae3_action` and identical stored payload must
   classify as `usable_tool_action`;
2. malformed arguments, an illegal action, a truncation receipt, a missing
   trace, and a non-identical stored tool payload must each fail in their named
   class; and
3. the async runtime tests in Plan #5 must pass.

Control failure stops the assay before spend.

## Evidence contract

The committed evidence bundle must contain:

- Git revision and clean/dirty state at dispatch;
- effective config, fixed state, both prompt files, rendered messages, and tool
  schema with SHA-256 hashes;
- one record per planned attempt including fixed case identity, latency, usage,
  cost, finish reason, terminal class, parsed action, and trace ID;
- every matching canonical receipt and exact retained call record, including
  `response_tool_calls` under full-content persistence;
- condition summaries, frozen verdict, actual aggregate spend, stop reason if
  any, and `SHA256SUMS` over the bundle.

No API keys, environment dumps, or provider-specific SDK objects are retained.
Results are appended below only after local gates pass and the frozen run ends.

## Results

Run once from clean revision `d9ad310c1275011df25dd8ff5951dd08ef2cf589`
on 2026-08-12 from 02:54:57Z through 03:03:14Z. All 32 frozen serial
attempts completed with no retry, timeout, truncation, cache hit, fallback
model, stop condition, or budget exhaustion. Actual aggregate cost was
USD 0.0359061.

### Frozen runner verdict

`not_qualified`. The frozen runner assigned `custody_failure` to all 32
attempts, so Evaluation 05 does not clear the instrument and no behavioral
evaluation may begin from this result.

That verdict exposed an assay implementation defect rather than 32 lost tool
payloads. `llm_client.observability.replay.get_call_record()` returned exact
messages, response content, and `response_tool_calls`, but its public record did
not include the SQLite-only `content_persistence` field. The Evaluation 05
classifier required that absent key to equal `full` before comparing payloads.
The SQLite rows themselves all recorded `content_persistence=full`.

### Post-run diagnostic audit (not a qualification decision)

The immutable evidence was audited without another model call:

| Condition | Attempts | Provider success | Exact successful tool payloads | Timeout / truncation | Descriptive usable actions |
|---|---:|---:|---:|---:|---:|
| prescribed | 16 | 16 | 16/16 | 0 / 0 | 16/16 |
| minimal | 16 | 15 | 15/15 | 0 / 0 | 15/16 |

The one minimal failure was `LLMEmptyResponseError`; its durable receipt and
call record were present. Across all 32 attempts, sent messages, caller-visible
response content, and reopened response content were identical; caller-visible
and reopened `response_tool_calls` were also identical (including the empty
failure record). Median/max latency was 10.2715/16.49 seconds for prescribed
and 13.033/56.291 seconds for minimal.

Those observations would meet the semantic 15/16 thresholds after correcting
the classifier, but they are explicitly not used to overwrite the frozen
verdict. The classifier now proves full custody through exact response/tool
equality and treats the persistence field as an additional check when the
readback API supplies it. A future qualification requires a new evaluation
number and preregistration; Evaluation 05 will not be rerun.
